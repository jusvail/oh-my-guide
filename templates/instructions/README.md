# Project instructions

Store one accepted project-specific topic in each Markdown file. Current code, tests, accepted architecture, repository
instructions, and the user's current request remain authoritative.

Each topic should state:

1. When it applies.
2. The required implementation pattern.
3. The pattern to avoid.
4. One concise real example when useful.
5. How to verify it.

Read only the topics relevant to the current decision; reuse unchanged instructions already in context. Apply instruction
priority and existing authorization before asking about a conflict. Ask only for incompatible requirements at the same
authority, missing material choices, or new authority. A natural-language request to save accepted knowledge is sufficient;
no special command is required.

Platform-specific validation topics must state their operating system and tool prerequisites. Separate target checks and
required product evidence from recovery steps; recover actual failures when a new action can help, not by a fixed retry
quota. Subjective user acceptance must be explicit.
